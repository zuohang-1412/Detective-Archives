### DAA-001 复现证据

- 角色：数据库中角色为 `EDITOR` 的真实测试用户。
- 请求：`POST /api/v1/admin/works/:id/status`，正文 `{"status":"PUBLISHED"}`。
- 修复前响应：HTTP 200，`data.status=PUBLISHED`；同一用户访问审核队列为 403，说明角色本身识别正确，缺陷位于作品状态授权。
- 根因：状态路由将 `EDITOR` 和 `ADMIN` 放在同一允许列表；作品更新和链接启用也没有区分草稿维护与发布动作。

### 修复说明

- EDITOR：可创建/编辑 `DRAFT` 或 `PENDING_REVIEW`，只能提交 `PENDING_REVIEW`；新建链接默认停用。
- ADMIN：可将待审作品发布、隐藏、恢复或归档，并启停链接。
- 已发布作品：EDITOR 修改返回 409 `WORK_NOT_EDITABLE`。
- 状态机从后台“草稿直接发布”改为“草稿 → 待审 → 发布 → 隐藏/恢复”。
- 无数据库迁移和历史数据修复需求；现有已发布内容由管理员或初始化过程产生，状态合法。

### DAA-002 复现与修复

- 根因：`Dockerfile` 的生产启动命令依次执行迁移和基础目录种子后直接启动 API，遗漏 `run-catalog-imports.mjs --apply`；现有数据库因开发阶段已单独导入，所以常规回归没有暴露问题。
- 影响：全新部署或灾备重建会缺少 124 条目录扩展记录和 114 部批次作品，不能达到当前发布数据口径。
- 修复：在服务监听前按清单应用 17 个不可变批次，并新增 `check:deployment` 检查启动顺序、非 root 用户、只读文件系统、禁止提权、回环端口和就绪探针。
- 回归：全新 PostgreSQL 隔离库依次应用 001～007、基础种子和 17 个批次，结果精确为 132 位人物、119 部作品、109 条图鉴，随后真实 DB API 生命周期通过。

## 5. 统一分析

本轮关闭两个 S1 缺陷：作品发布权限越权，以及生产冷启动遗漏目录批次。前者采用路由授权、仓储条件更新、链接默认状态和后台按钮四层一致约束；后者采用启动顺序修复、空库冷启动和部署静态检查三层防线。相关回归未发现新的 S0/S1 问题。

剩余风险不是代码缺陷，但会直接阻止全量发布：真实微信 `code2Session`、平台隐私声明、备案 HTTPS 域名和生产部署回滚尚无外部证据。内存限流适合当前单实例；未来扩容需改为共享存储。外链巡检中的 43 条网络不确定项需由运营按批复核，但当前没有确认失效地址。
